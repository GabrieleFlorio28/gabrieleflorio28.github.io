Vulnerable Lab -- Laboratorio Didattico Containerizzato

Un ambiente multi-container controllato, progettato con Docker e Docker Compose, volto a facilitare l'apprendimento delle vulnerabilità di rete e applicative più comuni, nonché delle relative contromisure ed analisi difensive.

TECNOLOGIE CHIAVE Docker, Docker Compose, Nginx, Linux, Python

La containerizzazione occupa oggi un ruolo centrale nello sviluppo e nella distribuzione del software: permette di eseguire servizi in ambienti isolati, riproducibili e trasferibili tra sistemi differenti. L'uso dei container, tuttavia, non rende un'applicazione automaticamente sicura. Vulnerabilità nel codice, configurazioni errate e scelte di isolamento poco rigorose possono compromettere l'intero ambiente.

Vulnerable Lab è un laboratorio didattico multi-container in cui osservare alcune vulnerabilità applicative e infrastrutturali in condizioni controllate. Ogni scenario è eseguito da un servizio distinto e collocato in una rete virtuale dedicata, limitando le comunicazioni ed evitando che la compromissione di un singolo servizio si estenda all'intero host.

La validazione combina test manuali di attacco, l'ispezione dello stato dei container tramite API Docker ed uno script automatico di test. Il risultato è uno strumento leggero e riproducibile per comprendere praticamente la relazione tra codice debole, configurazioni di rete e politiche di isolamento.

Reverse Proxy (Gateway)

Rete: external_net & subnets

Funge da unico punto d'accesso pubblico verso il laboratorio. Riceve le connessioni degli utenti esterni e le instrada, tramite regole di proxy-pass, ai corrispondenti container interni basandosi sul percorso URL.

Nginx Docker network
MISURA DI SICUREZZA: ISOLAMENTO DEL NETWORK Nginx è l'unico container connesso sia ad internet sia alle reti interne dei singoli scenari. Gli scenari applicativi non possono comunicare tra loro né con l'esterno, prevenendo attacchi laterali qualora un container venga compromesso.

SQL Injection Scenario

Rete: subnet_sqli | IP: 10.10.1.2

Web app vulnerabile in cui i parametri di ricerca o di login inviati dall'utente vengono concatenati direttamente in una query SQL senza alcuna sanitizzazione o parametrizzazione.

Python (Flask) SQLite
VULNERABILITÀ E ATTACCO SIMULATO Inserendo payload SQL (es. ' OR '1'='1) nei campi di input, l'attaccante aggira il controllo di login ed estrae credenziali o bypassa la verifica di autenticazione.

MITIGAZIONE: Implementazione di Prepared Statements (query parametrizzate) per separare rigidamente la logica di programmazione dai dati inseriti dall'utente.

Broken Authentication

Rete: subnet_auth | IP: 10.10.2.2

Gestione delle sessioni insicura o logica di autenticazione debole, che permette a terzi di rubare o indovinare i token utente.

Node.js / Python JWT
VULNERABILITÀ E ATTACCO SIMULATO I token di sessione (o JSON Web Token) sono firmati con chiavi deboli (bruteforceable) o configurati in modo tale che il server accetti algoritmi di firma nulli ("alg": "none"). L'attaccante può forgiare token amministrativi validi modificando il payload e firmandolo autonomamente.

MITIGAZIONE: Firma dei JWT tramite chiavi crittografiche robuste custodite in variabili d'ambiente protette, e imposizione forzata di algoritmi di crittografia sicuri lato server.

Privilege Escalation / Socket Mounting

Rete: subnet_priv | IP: 10.10.3.2

Uno scenario infrastrutturale critico che illustra l'impatto del montaggio non sicuro di risorse sensibili dell'host (come il socket di Docker) all'interno di un container non privilegiato.

Docker Daemon Alpine Linux
VULNERABILITÀ E ATTACCO SIMULATO Il volume montato /var/run/docker.sock permette al software all'interno del container di inviare comandi direttamente al demone Docker dell'host. Un utente malintenzionato che compromette questo container può lanciare un nuovo container con privilegi di root, montando il disco root dell'host (/) ed ottenendo così il controllo totale della macchina fisica/virtuale ospitante.

MITIGAZIONE: Evitare l'esposizione del socket Docker nei container. Utilizzare API astratte o proxy sicuri (come Socat) limitati in sola lettura, e applicare principi di Least Privilege (es. container rootless).

Security Misconfiguration

Rete: subnet_config | IP: 10.10.4.2

Configurazione errata di servizi di sistema, come file system esposti, interfacce di amministrazione prive di password, o modalità debug attive in produzione.

Apache / Nginx Config Files
VULNERABILITÀ E ATTACCO SIMULATO Directory Listing abilitato sul server web, accoppiato ad un database di backup non protetto lasciato accidentalmente nella cartella pubblica. L'attaccante può navigare l'albero delle directory del server tramite browser e scaricare file riservati (es. file .env o backup SQL).

MITIGAZIONE: Disabilitare rigorosamente il listing delle directory (autoindex off;), ripulire i server di produzione dai file temporanei o di backup e disattivare i messaggi di errore dettagliati.

Script Automatico di Test

Rete: test_net (connesso alle singole subnets)

Uno script Python automatizzato implementato nel laboratorio per verificare l'effettiva presenza delle vulnerabilità, convalidare i canali di exploit e testare la robustezza dei container.

Python 3 Requests Lib Docker SDK
VERIFICA E VALIDAZIONE Lo script esegue automaticamente richieste HTTP con payload d'attacco verificando la risposta ricevuta. Esegue inoltre chiamate dirette all'API del demone Docker per sincerarsi che l'isolamento tra subnets sia costantemente rispettato e che i container abbiano privilegi limitati.
