Vulnerable Lab — Laboratorio Didattico Containerizzato

Un ambiente multi-container controllato, progettato con Docker e Docker Compose, per lo studio pratico delle vulnerabilità web e applicative più comuni. Ogni scenario è un servizio Flask indipendente, isolato nella propria rete Docker dedicata.

TIPO DI PROGETTO Tesi di Laurea Triennale in Informatica
DATA DI LAUREA 25 Settembre 2026
TECNOLOGIE CHIAVE Docker, Docker Compose, Flask, SQLite, Python
UNIVERSITÀ Università degli Studi di Catania
cat tesi_abstract.txt

La containerizzazione occupa oggi un ruolo centrale nello sviluppo e nella distribuzione del software: permette di eseguire servizi in ambienti isolati, riproducibili e trasferibili tra sistemi differenti. L'uso dei container, tuttavia, non rende un'applicazione automaticamente sicura. Vulnerabilità nel codice, configurazioni errate e scelte di isolamento poco rigorose possono compromettere l'intero ambiente.

Vulnerable Lab è un laboratorio didattico multi-container in cui osservare alcune vulnerabilità applicative e infrastrutturali in condizioni controllate. Ogni scenario è implementato come un servizio Flask distinto, orchestrato da Docker Compose e collocato in una rete virtuale dedicata (sql_net, auth_net, priv_net, misconf_net), garantendo l'isolamento tra i servizi.

La validazione è affidata a uno script PowerShell automatizzato (test-lab.ps1) che invia richieste HTTP con payload d'attacco a ciascuno scenario, verificando le risposte. Il risultato è uno strumento leggero e riproducibile per comprendere praticamente la relazione tra codice debole, configurazioni errate e politiche di isolamento.

Docker Compose — Orchestrazione

File: docker-compose.yml | 4 servizi, 4 reti isolate

Docker Compose orchestra l'intero laboratorio definendo quattro servizi indipendenti, ciascuno costruito dal proprio Dockerfile e collocato nella propria rete Docker dedicata. Ogni servizio espone una porta diversa sull'host locale (5000–5003).

Docker Docker Compose Dockerfile
ISOLAMENTO ARCHITETTURALE Ogni scenario è assegnato ad una rete Docker separata (sql_net, auth_net, priv_net, misconf_net). I container non condividono la stessa rete e non possono comunicare direttamente tra loro, limitando la superficie d'attacco laterale in caso di compromissione di un singolo servizio.

SQL Injection Scenario

Rete: sql_net | Porta: localhost:5000

Applicazione Flask vulnerabile che utilizza SQLite come database. I parametri di ricerca inviati tramite query string (/search?q=) vengono concatenati direttamente nelle query SQL senza sanitizzazione né parametrizzazione, permettendo l'iniezione arbitraria di codice SQL.

Python (Flask) SQLite
VULNERABILITÀ E ATTACCO SIMULATO L'endpoint /search?q= accetta input non filtrato. Inserendo payload come ' OR '1'='1 nel parametro di ricerca, l'attaccante può estrarre l'intero contenuto del database, bypassare controlli di autenticazione e manipolare i dati. L'endpoint /init inizializza il database con dati di esempio.

MITIGAZIONE: Utilizzo di Prepared Statements (query parametrizzate) per separare rigidamente la logica SQL dai dati inseriti dall'utente, impedendo l'esecuzione di codice iniettato.

Broken Authentication

Rete: auth_net | Porta: localhost:5001

Applicazione Flask con un sistema di autenticazione volutamente insicuro: le credenziali utente sono memorizzate in chiaro nel codice sorgente come dizionario Python (alice:password123, bob:qwerty), senza alcun meccanismo di hashing o salting.

Python (Flask) Plaintext Passwords
VULNERABILITÀ E ATTACCO SIMULATO Le password sono conservate in chiaro nel codice sorgente. L'endpoint /login accetta credenziali via POST e le confronta direttamente con il dizionario in memoria. Un attaccante che ottiene accesso al codice sorgente o al container può leggere immediatamente tutte le credenziali. L'uso di password deboli (password123, qwerty) rende il sistema vulnerabile ad attacchi di forza bruta.

MITIGAZIONE: Hashing delle password con algoritmi robusti (bcrypt, argon2), utilizzo di salt univoci per ogni utente, e conservazione delle credenziali in un database separato con accesso controllato.

Privilege Escalation

Rete: priv_net | Porta: localhost:5002

Scenario Flask che simula un servizio con accesso improprio a risorse privilegiate. Il container illustra come un'errata configurazione dei permessi o il montaggio di risorse sensibili dell'host possa permettere l'escalazione dei privilegi.

Python (Flask) Docker Volumes
VULNERABILITÀ E ATTACCO SIMULATO Il servizio espone funzionalità che permettono l'accesso a risorse che dovrebbero essere ristrette. Un utente non privilegiato può sfruttare endpoint non protetti per ottenere informazioni o eseguire operazioni che richiederebbero permessi elevati, dimostrando l'importanza del principio di Least Privilege nella progettazione dei container.

MITIGAZIONE: Applicare il principio di Least Privilege: eseguire i processi con utenti non-root, limitare i volume mounts allo stretto necessario, e utilizzare container rootless o policy di sicurezza (seccomp, AppArmor).

Security Misconfiguration

Rete: misconf_net | Porta: localhost:5003

Applicazione Flask avviata con la variabile d'ambiente DEBUG_MODE=true impostata nel docker-compose.yml. Simula un errore di configurazione tipico in ambienti di produzione: modalità debug attiva, esposizione di informazioni interne e messaggi di errore dettagliati.

Python (Flask) Environment Variables DEBUG_MODE
VULNERABILITÀ E ATTACCO SIMULATO La variabile DEBUG_MODE=true definita nel Compose attiva la modalità debug di Flask, che espone il debugger interattivo di Werkzeug in caso di errore. Un attaccante può provocare un'eccezione ed accedere alla console di debug, eseguendo codice Python arbitrario sul server. I messaggi di errore dettagliati rivelano stack trace, percorsi di file e variabili d'ambiente.

MITIGAZIONE: Non impostare mai DEBUG_MODE o FLASK_DEBUG in ambienti di produzione. Utilizzare variabili d'ambiente gestite in modo sicuro, disabilitare messaggi di errore verbosi e implementare pagine di errore personalizzate.

Script Automatico di Test

Script: scripts/test-lab.ps1 | Host locale

Uno script PowerShell (test-lab.ps1) che automatizza la verifica del laboratorio. Lo script invia richieste HTTP ai vari endpoint vulnerabili con payload d'attacco predefiniti, verifica le risposte ricevute e produce un report sullo stato di ciascuno scenario.

PowerShell Invoke-WebRequest Automazione Test
VERIFICA E VALIDAZIONE Lo script testa automaticamente ciascun endpoint: invia query SQL malevole a :5000, tenta login con credenziali deboli su :5001, verifica l'accesso a risorse privilegiate su :5002 e controlla l'esposizione del debugger su :5003. I risultati vengono confrontati con le risposte attese per validare il corretto funzionamento degli scenari.
